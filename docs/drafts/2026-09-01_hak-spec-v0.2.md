## 1. Purpose

A small LAN service that gives human and agent seats a **persistent, shared, auditable
message space** per project ("room"), replacing today's implicit channels:

| Today (implicit) | Problem | HAK replacement |
|---|---|---|
| Human relays notes/screenshots between agents | human is a router; format loss (vision OCR) | direct seat-to-seat messages + attachments |
| dark-factory/notes turn files | conventions only; no history query; no presence | typed, queryable envelopes |
| A2A bridge | context deleted after each task; 500s on message/stream | rooms persist; history is the context |
| Backend churn (MiMo retired, GLM in, ...) | communication history dies with the backend | **seats are stable, backends are swappable** |

Design stance: **pull-first** (agent runtimes are turn-based and cannot receive mid-turn
pushes), **Git stays the artifact bus** (HAK is coordination, pointers and history —
not an artifact store), **peer seats over an orchestrator** (memento §2: scopes +
statuses + handovers; no decomposition, no step assignment, no scheduling).

### Non-goals (v1)

- No orchestration/delegation/dispatch — coordination is claims, statuses, handovers.
- No agent-runtime integration plugins, no mid-turn push, no SSE (v2 at the earliest).
- No E2E encryption (LAN trust domain), no federation, no search (v2 candidate: SQLite FTS5).
- No large artifact storage — files by reference (URI + sha256); small attachments only.

## 2. Concepts

| Concept | Definition |
|---|---|
| **Room** | Thematic workspace, e.g. `bdh-cl-development`. Has a **charter** (purpose, admin, member list, and per §8 a dispatch table; optional `repo_url`/`project` linkage, D8/Danwa 2.5), one message history with total order, optional attachments. Created and administered by the human (v1). |
| **Seat** | Stable identity of a participant, from the IDENTITIES.md register (`operator`, `quinn`, `pi-203`, `pi-50`, `glm-flash`, ...). Seats outlive backends. |
| **Backend** | The LLM currently serving a seat, recorded per message (like commit trailers / report headers). Pure metadata — never used for auth. |
| **Token** | Bearer secret per seat, issued by the admin, revocable. The only auth artifact. |
| **Envelope** | One immutable message (schema §5). The only payload type on the bus. |
| **Cursor** | A room sequence number (`seq`). Clients pull `?since=<seq>`. The server also tracks `last_read_seq` per member (unread counts, "seen" — a UX read model, Q6 split upheld). |
| **Retraction** | The only way to "un-say" something: a new message of `type=retraction` with `reply_to` pointing at the original. History is append-only (provenance culture; see the F5/konfabulation lessons). |
| **Scope claim** | A lease on a resource URI (`file://`, `gpu://`, `host://`, `model://`), held by a seat for a TTL, recorded as events (D2). Write claims are mandatory for repo/tree paths (charter rule). |
| **Handover** | An `artifact_ref` with `meta.kind="handover"` (optionally `meta.for_seat`), pullable as "open handovers for me" — the typed replacement for luck-based pickup (memento §4.3). |
| **Projector** | A derived read model over the append-only history (live claims, last_read, presence strip, later: FTS5). Projectors can be added/dropped without touching the write path (Danwa 2.3). |

## 3. Architecture (proposed, minimal)

- **Stack:** FastAPI + SQLite (WAL mode), single container or systemd unit, ~500–1.000 LOC.
- **Placement:** open — decision §16 Q1.
- **Network:** bind LAN interface only; TLS optional via reverse proxy later.
- **Storage:** one SQLite file (`hak.db`) + one uploads dir. Backup = file copy / litestream (later).
- **Ordering:** single-writer total order per room via SQLite transaction; `seq` per room, 1-based, gapless.

### 3.1 Event / projector split (D2, D8)

The messages table and the scope-events table are append-only logs. Everything mutable a
client sees — liveness of a claim, unread badges, the presence strip — is a **projector**
over a log, recomputable from seq 0. Rule: *nothing that can change retroactively is
stored; it is derived.* This is the same shape Danwa validated in production (four
projectors over one event log) and it is what makes D2's replay guarantee cheap.

## 4. Auth and join flow

1. Admin issues a token per seat (CLI or endpoint), stores only the hash.
2. Seat calls `POST /v1/rooms/{room}/join` with its token → membership status `pending`.
3. Admin approves via Web UI or `POST /v1/rooms/{room}/members/{seat}/approve` → `member`.
4. Revocation (`revoke`) disables the token immediately (backend-churn / offboarding).

The human is seat `operator` with role `admin` in every room. Room creation is admin-only (v1).
Join confirmation requirement is deliberate: no silent self-enrollment of agents.

## 5. Envelope schema

```json
{
  "seq": 4711,                      // server-assigned, per-room monotonic, gapless
  "id": "m_0000004711",             // stable handle for reply_to / links
  "client_msg_id": "pi203-9f3a",    // client-supplied (D4); server dedupes on it; optional
  "room": "bdh-cl-development",
  "ts": "2026-09-01T21:40:12.312+02:00",
  "from": {"seat": "pi-203", "backend": "glm-5.3"},   // backend optional, free string (Q3 proposal)
  "to": {"seat": "pi-50"},          // null → broadcast to the room
  "type": "chat",                   // closed set, §6
  "reply_to": "m_0000004699",       // optional; thread root = first message of chain (Q7 proposal)
  "body": "Phase 13 (fi) complete: INIT=ro_last, width 512, step 10000/10000.",
  "attachments": [                  // small files only (default cap 25 MB/file, Q4 proposal)
    {"file_id": "f_a1b2c3", "name": "fi_log_tail.txt", "content_type": "text/plain",
     "sha256": "...", "size": 4123}
  ],
  "refs": [                         // artifact pointers — the Git-bus integration
    {"uri": "https://github.com/asb-42/bdh/commit/a945438", "note": "checklist addendum 5"}
  ],
  "meta": {                          // kind-disciplined (D3, D7); context, never conversation content
    "kind": "status",               // "status" | "response" | "admin-op" | (room-defined)
    "state": "working_on",          // status: working_on | waiting_on | blocked | done
    "ref": "file:///media/data/coding/weight-atlas",
    "note": "ngram streaming, step 4200/10000",
    "eta": "2026-09-01T23:00:00+02:00"
  }
}
```

**`meta` discipline (normative):** every `meta` object carries exactly one `kind`.
`meta` is additional data — never conversation content (ACP/Danwa rule). Recognized kinds:

| kind | Carried by | Fields |
|---|---|---|
| `status` | `type=status` | `state` ∈ {working_on, waiting_on, blocked, done}, `ref`, `note`, optional `eta` (memento §4.2, relocated per D3) |
| `handover` | `type=artifact_ref` | optional `for_seat` (directed handover); makes "open handovers for me" a single filtered pull (memento §4.3) |
| `response` | `type=task_result`, `type=review_verdict` | marker only — clients MUST NOT auto-respond (§8.2) |
| `admin-op` | system envelopes (`from.seat="hak"`) | `op` ∈ {member_approve, member_revoke, token_issue, token_revoke, room_create}, `target` |

**System envelopes (D6):** every admin-privileged operation appends an envelope with
`from.seat="hak"`, human-readable `body`, and `meta.kind="admin-op"`. The room audit
trail is therefore replayable like everything else — no side channel.

## 6. Type vocabulary (v1, closed set — unchanged from v0.1)

| type | meaning |
|---|---|
| `chat` | ordinary conversation |
| `status` | heartbeat/status; structured fields in `meta.kind="status"` |
| `task_request` | request for work or status from another seat (expects `task_result`) |
| `task_result` | answer to a `task_request` (threaded via reply_to; `meta.kind="response"`) |
| `artifact_ref` | pointer to a commit/report/file (+ sha256); `meta.kind="handover"` + optional `meta.for_seat` marks a handover |
| `review_verdict` | structured review outcome (pass/fail + findings pointer; `meta.kind="response"`) |
| `retraction` | corrects/retracts a prior message (reply_to mandatory) |

The set stays deliberately small. Everything structured-but-unlisted goes through `chat`
plus a room-defined `meta.kind` until the design phase promotes it (fat-event rule:
new capability = new metadata, never a new type).

## 7. Endpoints (v1)

All require `Authorization: Bearer <token>`. JSON in/out.

### Rooms & membership

```
GET  /v1/health
GET  /v1/rooms    # rooms the token can see
POST /v1/rooms    # admin: {name, charter}
GET  /v1/rooms/{room}    # charter, members, admin
POST /v1/rooms/{room}/join    # → pending
POST /v1/rooms/{room}/members/{seat}/approve     # admin
POST /v1/rooms/{room}/members/{seat}/revoke      # admin (kills token)
GET  /v1/rooms/{room}/members    # incl. last_poll (soft presence), last_read_seq
```

### Messages — push & pull

```
POST /v1/rooms/{room}/messages                   # envelope minus seq/id/ts; to=null → broadcast
                                                 # client_msg_id honored for dedupe (D4):
                                                 # duplicate → 200 with the original envelope
                                                 # new        → 201 with the stored envelope
GET  /v1/rooms/{room}/messages                   # THE workhorse (pull):
     ?since=<seq> &until=<seq> &from=<seat> &to=<seat|null>
     &type=<t> &thread=<msg_id> &meta_kind=<kind> &for_seat=<seat>
     &limit=100 (max 500) &order=asc|desc
GET  /v1/rooms/{room}/messages/{id}
POST /v1/rooms/{room}/read    # {"seq": 4711} → set member's last_read_seq
```

Pull semantics: `since` returns messages with `seq > since` in ascending order — a cursor
that survives server restarts, client restarts, and gaps. An agent that polls at every
seam never misses anything and never double-processes (idempotent by seq). New filters:
`meta_kind` (e.g. `handover`) and `for_seat` make "open handovers for me" one query
(memento §4.3).

### Scope claims (D2 — events, projector-backed)

```
POST   /v1/rooms/{room}/scopes            # {resource_uri, kind, note?, ttl_min?} → 201 {scope_id, expires_at}
                                         # conflict → 409 {conflicting: {holder, kind, expires_at}} — never silently queued
POST   /v1/rooms/{room}/scopes/{id}/renew # extends TTL → 200 {expires_at}
DELETE /v1/rooms/{room}/scopes/{id}       # release → 204
GET    /v1/rooms/{room}/scopes?active=1  # live claims (projector view; presence strip reads this)
```

- `kind`: `write` | `read-exclusive` | `exclusive` | `share[n]` | `reserve` (memento §4.1).
- Conflict rule at claim time: exclusive vs. any → 409; share kinds advertise capacity
  (charter policy, not hardcoded).
- Claim, renew, release are **events**; `expires_at` is derived from the last event +
  TTL. A crashed seat cannot deadlock a resource: the projector stops presenting the
  claim after TTL without any write. A compaction pass may append a `lapse` marker for
  replay clarity (never rewrites history).
- Convention (charter rule, one line): **write claims are mandatory for repo/tree
  paths**; read seats never claim and are unlimited.

### Files

```
POST /v1/files        # multipart upload, size-capped → {file_id, sha256, size, name, content_type}
GET  /v1/files/{id}   # download (content-type preserved)
```

Large artifacts never go through here: use `refs` with URI + sha256 and keep the payload
in Git / /srv/coding. Uploads are for the screenshot-class of things the human had to
relay by hand.

### Admin/ops

```
POST /v1/tokens    # admin: issue token for a seat
POST /v1/tokens/{token_id}/revoke
```

Every admin/ops call appends its system envelope (D6) before returning.

## 8. Delivery semantics

1. **Total order** per room (seq, gapless, single writer). Timestamps are informational.
2. **Broadcast** = visible to all room members (membership-based, not presence-based).
   Presence (last_poll) is cosmetic in v1.
3. **Direct messages** are recorded in the same room history with a `to` field and are
   **readable by all members** — transparent bus, no hidden channels (Q2 proposal).
   If a truly private channel is ever needed, spin up a separate room.
4. **At-least-once processing is the client's job via cursors**; emission is
   exactly-once via `client_msg_id` (D4). Store your last processed seq, poll `since`,
   process, advance. Server-side `last_read_seq` is for unread/seen UX only (Q6 split).

### 8.1 Cursor discipline (normative — D5)

- **Record your cursor *before* issuing a `task_request`** (subscribe-before-trigger,
  Danwa 2.1): closes the gap between "request sent" and "next poll" — the race Danwa
  explicitly engineered away.
- **Process the batch fully, then persist the cursor.** A crash mid-batch replays from
  the last processed seq (write-ahead discipline; at-least-once processing with
  idempotent handling by seq).

### 8.2 Loop guard (normative — D5, Danwa 2.2)

Messages carrying `meta.kind="response"` (`task_result`, `review_verdict`) MUST NOT
auto-trigger a further response. A client may surface them, may act on them when its
user/operator asks — but reflex-like polling logic must skip them. This prevents
agent ping-pong storms the moment any seat gets reflex-like polling logic.

### 8.3 Dispatch table (charter field — Danwa 2.4)

Each room charter records who consumes what. v1 is deliberately trivial:

| seat class | consumes | emits |
|---|---|---|
| human (`operator`) | reads all | `chat`, admin ops |
| agent seats | pull all types | `chat`, `status`, `task_request`, `task_result`, `artifact_ref`, `review_verdict`, `retraction` |

Per-seat `subscriptions` is a v2 candidate. Writing the trivial table down now
prevents implicit conventions later.

5. **Immutability:** no edits, no deletes. Corrections are `retraction` messages.
6. **No mid-turn push in v1.** Agents poll at seams (turn start/end, tool-call
   boundaries). SSE/long-poll is v2 and only ever an optimization of the same cursor
   semantics.

## 9. Human Web UI (requirements, not implementation)

- Chat-like view: room list with unread badges, message stream, thread view (reply_to),
- Composer: text, type selector, attach small file, reply/broadcast toggle.
- Admin panel: pending join requests → approve/revoke, token issue/revoke, charter display.
- Filters: by seat, type, thread, `meta.kind`. Attachment previews for images (the screenshot case).
- Read state: marks last_read automatically; shows per-member last_poll and last_read.
- **Presence strip (memento §4.2):** one line per seat from the latest
  `meta.kind="status"` envelope — current state + ref — beside the live scope claims
  (`GET /scopes?active=1`). This alone dissolves the "is this duplicate work?"
  interruption: the strip would have shown both seats' live states.

## 10. Agent client guidance

- Token in env var (`HAK_TOKEN`), base URL in (`HAK_URL`, e.g. `http://gx10:8890`) — renamed per D1.
- Poll at **seams**: turn start (catch up: `GET messages?since=<cursor>`), after finishing
  a work item (`status` or `task_result`), before ending the turn.
- Prefer filtered pulls (`type=status`, `meta_kind=handover&for_seat=me`) over full-history reads.
- Record `backend` in every message (convention from IDENTITIES.md — same as commit trailers).
- Honor §8.1/§8.2 cursor discipline and loop guard.
- **Claim before you write** (charter rule): `POST /scopes` with `resource_uri=file://...`
  before touching a repo/tree; renew as part of the working loop; release when done.
- Minimal client is five calls (memento §5): `claim(resource)`, `renew()`, `release()`,
  `status(state, ref)`, `pull(since)` — invoked at seams. For OpenCode it wraps the
  existing note/commit workflow; for A0 into tool calls; for pi seats, the bridge
  extension implements it once for every seat (implementation phase, after design go).

```bash
curl -s "$HAK_URL/v1/rooms/bdh-cl-development/messages?since=$CURSOR&limit=200" \
     -H "Authorization: Bearer $HAK_TOKEN"
curl -s "$HAK_URL/v1/rooms/bdh-cl-development/messages" \
     -H "Authorization: Bearer $HAK_TOKEN" -H "Content-Type: application/json" \
     -d '{"type":"status","client_msg_id":"pi203-0042","to":null,"body":"phase 15 (bg) step 4200/10000, on schedule","meta":{"kind":"status","state":"working_on","ref":"file:///media/data/coding/weight-atlas","eta":"2026-09-01T23:00:00+02:00"}}'
```

## 13. Scope

**v1 (implementation candidate after design phase):** rooms + charter (incl. dispatch
table, repo linkage), join/approve/revoke, tokens, envelopes (7 types + meta kinds),
broadcast + direct (transparent), idempotent emission (`client_msg_id`), cursor pulls +
normative cursor discipline, read cursors, **scope claims (events + projector)**,
**status envelopes**, **handover refs**, small attachments, artifact refs, system
envelopes for admin ops, human Web UI (incl. presence strip), agent API, conformance
script (§15). No push, no SSE, no search, no server-side dispatch.

**v2 candidates:** SSE/long-poll, presence beyond last_poll, per-seat `subscriptions`,
typed webhooks (e.g. into notify_user for the operator), FTS5 search (as projector),
per-room retention policy, cross-room scopes (only if a real case appears), `@-mention`
wake (Q13).

## 14. Security notes

- Tokens: 32+ random bytes, shown once, stored hashed; revocation is immediate.
- LAN-only bind; optional TLS via reverse proxy (v2); no public exposure, ever.
- Uploads: served only from the uploads dir with generated names; no path traversal;
  size cap enforced before accept; MIME not trusted for execution. `content_type` is
  descriptive (D7), never an execution hint.
- The message history is the audit trail — append-only by design; admin-privileged
  operations are system envelopes in the room they affect (D6), not log lines elsewhere.
- Scope claims carry no authority: they are coordination signals, not locks. A claim
  does not (and cannot) enforce anything at the filesystem level; enforcement remains
  seat discipline + review, exactly as today — the claim makes the discipline *visible*.

## 15. Acceptance criteria (normative — gates v1)

The conformance script ships with the implementation and must pass C1–C8 before any
deployment. Criteria from memento §6 are carried and extended.

- **C1 Scope conflict:** two exclusive claims on one resource → second gets 409 with
  holder + expiry; both visible in history/events.
- **C2 Crash safety:** a claim without renewal expires via the projector ≤ TTL after
  process death; the resource is reclaimable without admin action.
- **C3 Handover determinism:** after an `artifact_ref` with `meta.kind="handover"`
  lands, the named seat's next seam-pull returns it (send, pull with fresh cursor,
  assert presence and order).
- **C4 Presence strip:** live states for ≥ 2 concurrent seats; a `done` status clears the line.
- **C5 Replay determinism:** byte-identical replay of a room from seq 0 — messages and
  scope events alike; projectors rebuilt from the log alone reach identical state.
- **C6 Idempotent emission:** the same `client_msg_id` POSTed twice → one envelope, two
  200/201 responses naming the same `id`.
- **C7 Cursor discipline:** a client crash mid-batch replays the full batch from the
  last persisted cursor; nothing between cursors is lost (replay over a kill -9 of the
  reference client).
- **C8 Loop guard:** a `task_result` addressed to a reflex-polling reference client
  never produces a second automated response (harness test).
