## 1. Purpose

A small LAN service that gives human and agent seats a **persistent, shared, auditable
message space** per project ("room"), replacing today's implicit channels:

| Today (implicit) | Problem | HAK replacement |
|---|---|---|
| Human relays notes/screenshots between agents | human is a router; format loss (vision OCR) | direct seat-to-seat messages + attachments |
| dark-factory/notes turn files | conventions only; no history query; no presence | typed, queryable envelopes |
| A2A bridge | context deleted after each task; 500s on message/stream | rooms persist; history is the context |
| Backend churn (MiMo retired, GLM in, ...) | communication history dies with the backend | **seats are stable, backends are swappable** |

Design stance: **pull-first** (agent runtimes are turn-based and cannot receive mid-turn
pushes), **Git stays the artifact bus** (HAK is coordination, pointers and history —
not an artifact store), **peer seats over an orchestrator** (memento §2: scopes +
statuses + handovers; no decomposition, no step assignment, no scheduling).

### Non-goals (v1)

- No orchestration/delegation/dispatch — coordination is claims, statuses, handovers.
- No agent-runtime integration plugins, no mid-turn push, no SSE (v2 at the earliest).
- No E2E encryption (LAN trust domain), no federation, no search (v2 candidate: SQLite FTS5).
- No large artifact storage — files by reference (URI + sha256); small attachments only.

## 2. Concepts

| Concept | Definition |
|---|---|
| **Room** | Thematic workspace, e.g. `bdh-cl-development`. Has a **charter** (§17: purpose, admin list, dispatch table, claim policy, attachment policy; optional `repo_url`/`project` linkage), one message history with total order, optional attachments. Created and administered by the human (v1). The charter records the initial admin list and dispatch rules; membership is derived from the membership table, not stored in the charter (D28). In v1 the charter is immutable after creation (D32). |
| **Seat** | Stable identity of a participant, from the IDENTITIES.md register (`operator`, `quinn`, `pi-203`, `pi-50`, `glm-flash`, ...). Seats outlive backends. `hak` is a reserved system actor, deliberately not in IDENTITIES.md — it exists only as the `from.seat` of system envelopes (D6) and holds no token (D24). |
| **Backend** | The LLM currently serving a seat, recorded per message (like commit trailers / report headers). Pure metadata — never used for auth. |
| **Token** | Bearer secret per seat, issued by the admin, revocable. The only auth artifact. A seat may hold **N tokens** (D19). Stored **hashed: SHA-256, unsalted** (D43) — 256+ bits of entropy; password-KDFs are overkill; revisit only if tokens become human-memorable. |
| **Envelope** | One immutable message (schema §5). The only payload type on the bus. |
| **Cursor** | A room sequence number (`seq`). Clients pull `?since=<seq>`. The server also tracks `last_read_seq` per member (unread counts, "seen" — a UX read model, Q6 split upheld). |
| **Retraction** | The only way to "un-say" something: a new message of `type=retraction` with `reply_to` pointing at the original — **own messages only; admin any; one effective retraction per target; a retraction cannot target a retraction** (D37). History is append-only (provenance culture; see the F5/konfabulation lessons). Rendering: visible but marked (D17). |
| **Scope claim** | A lease on a resource URI (`file://`, `gpu://`, `host://`, `model://`), held by a seat for a TTL, recorded in the **scope log** (D14) as events. Write claims are mandatory for repo/tree paths (charter rule). Conflict identity = exact normalized URI; capacity class by scheme (D34). |
| **Scope log** | The separate append-only log of claim/renew/release/lapse events (§3.1), with its own per-room `scope_seq`. Not the message history; not pullable via `GET /messages`. History pulls take `?since=<scope_seq>` (D35). |
| **Handover** | An `artifact_ref` with `meta.kind="handover"` (optionally `meta.for_seat`), pullable as "open handovers for me" — the typed replacement for luck-based pickup (memento §4.3). |
| **Projector** | A derived read model over an append-only log (live claims, last_read, presence strip, later: FTS5). Projectors can be added/dropped without touching the write path (Danwa 2.3). |
| **Charter** | The single authoritative policy document for a room (§17): admins, dispatch table, claim policy (default TTL, share capacities), attachment policy. **`admins` is the sole authoritative admin set** (D32); in v1 the charter is immutable after creation; mutation through the service only, as `admin-op: charter_update` in a future endpoint (D28/D32). |

## 3. Architecture (proposed, minimal)

- **Stack:** FastAPI + SQLite (WAL mode), single container or systemd unit. Small conceptual surface over any LOC count (M3): explicit code with tests beats compressed cleverness.
- **Placement:** open — decision §16 Q1.
- **Network:** bind LAN interface only; TLS optional via reverse proxy later.
- **Storage:** one SQLite file (`hak.db`) + one uploads dir. **Backup:** SQLite Online Backup API or `VACUUM INTO` — a plain file copy of a live WAL database is insufficient and is not a valid backup path (D38). `hak.db` and `uploads/` are **one backup unit**; a restore with one but not the other violates attachment references (D38).
- **Ordering:** single-writer total order per room via SQLite transaction; `seq` per room, 1-based, gapless. The scope log has its own per-room `scope_seq`, same properties (D14).
- **SQLite ops (D21/D23):** WAL checkpointing stays PASSIVE (default) at this scale; VACUUM is unnecessary for the logs themselves (append-only; `VACUUM INTO` remains valid as a backup mechanism, D38). Under WAL + `BEGIN IMMEDIATE` the single writer may queue briefly on the write lock — readers never block; LAN-scale writes are sub-second. `ts` is NTP-disciplined server wall time, informational (D21).

### 3.1 Event / projector split (D2, D8, D14)

Two append-only logs — messages and scope events — and everything mutable a client
sees is a **projector** over a log, recomputable from its beginning: liveness of a
claim, unread badges, the presence strip, later FTS5. Rule: *nothing that can change
retroactively is stored; it is derived.* This is the same shape Danwa validated in
production and it is what makes the replay guarantee (C5b) cheap.

### 3.2 Resource normalization (D34)

Resource URIs must parse. The scheme is normalized lowercase. **Conflict identity =
exact normalized URI** — `gpu://foo` and `gpu://foobar` are distinct resources.
**Capacity class is determined by scheme** (gpu, host, file, model) — not by arbitrary
string prefix (supersedes D28's `startswith` rule). Share counting is per `(room,
resource)` within the scheme's charter capacity.

## 4. Auth and join flow

1. Admin issues a token per seat (CLI or endpoint), stores only the hash. A seat may
   hold N tokens (D19); member-revoke kills all of them, token-revoke kills one.
   **Token issuance is bound to the seat registry** (host-local seats file mirroring
   IDENTITIES.md; enforced server-side, not convention — D43).
2. Seat calls `POST /v1/rooms/{room}/join` with its token → membership status `pending`.
3. Admin approves via Web UI or `POST /v1/rooms/{room}/members/{seat}/approve` → `member`.
4. Revocation (`revoke`) disables the token(s) immediately (backend-churn / offboarding)
   — a revoked token gets 401 on its next request (D24).

The human is seat `operator`. **Room creation MUST insert `operator` into
`charter.admins`; `admins` is the sole authoritative admin set** (D32). Join
confirmation requirement is deliberate: no silent self-enrollment of agents.

### 4.1 Membership state machine (D36, normative)

| Membership | Token | Result |
|---|---|---|
| `pending` | valid | join only — 403 on every other endpoint |
| `member` | valid | normal access |
| `revoked` | valid | 403 |
| any | revoked | 401 |

Rejoin after revoke creates a **new** `pending` membership (authorization is rebuilt;
history visibility follows the new approval). Member re-join is idempotent (200, no
new row). Token validity and membership stay orthogonal, as designed. The §2/§17
distinction stands: membership is derived state; the charter records only the initial
admin list and dispatch rules.

## 5. Envelope schema

```json
{
  "seq": 4711,                      // server-assigned, per-room monotonic, gapless
  "id": "m_0000004711",             // stable handle for reply_to / links
  "client_msg_id": "pi203-9f3a",    // client-supplied (D4/D11); unique per (room, seat); optional
  "room": "bdh-cl-development",     // server-derived from the path (D10)
  "ts": "2026-09-01T21:40:12.312+02:00",  // server-assigned (D10) — NTP-disciplined wall clock,
                                          // informational (D21); mixed-seat clock skew must not
                                          // bend the audit trail; seq is the order of record
  "from": {"seat": "pi-203", "backend": "glm-5.3"},  // server-derived from the token (D10);
                                                     // backend is the client's free string (Q3)
  "to": {"seat": "pi-50"},          // null → broadcast to the room
  "type": "chat",                   // closed set, §6
  "reply_to": "m_0000004699",       // optional; thread root = first message of chain (Q7)
  "body": "Phase 13 (fi) complete: INIT=ro_last, width 512, step 10000/10000.",
  "attachments": [                  // small files only (charter cap, Q4; room-scoped, D29)
    {"file_id": "f_a1b2c3", "name": "fi_log_tail.txt", "content_type": "text/plain",
     "sha256": "...", "size": 4123}
  ],
  "refs": [                         // artifact pointers — the Git-bus integration
    {"uri": "https://github.com/asb-42/bdh/commit/a945438", "note": "checklist addendum 5"}
  ],
  "meta": {                          // kind-disciplined (D3, D7, D39); context, never conversation content
    "kind": "status",               // closed set v1 (D39): status | handover | response | admin-op
    "state": "working_on",          // status: working_on | waiting_on | blocked | done
    "ref": "file:///media/data/coding/bdh",
    "note": "phase 13 (fi), step 10000/10000 — complete",
    "eta": null
  }
}
```

**POST contract (normative, D10):** the client sends the envelope minus
`seq/id/ts/from/room`. The server derives `from` from the bearer token and `room` from
the path, assigns `seq`, `id`, `ts`, and **rejects with 422 any client-supplied value
for these five fields** — provenance is not negotiable on a bus whose core promise is
auditability (C10).

**Timestamp semantics (D21):** `ts` is the server's NTP-disciplined wall clock —
informational; `seq` is the order of record (D10).

**Canonicalization (D31, normative):** the idempotency hash input is **the normalized
POST object after schema validation, serialized per RFC 8785 (JSON Canonicalization
Scheme)**. Schema validation normalizes **omitted == null** for all optional fields —
both forms hash identically. One rule, two closures: the same canonical serialization
defines C5a's replay identity. Emission semantics: **exactly-once logical persistence
per idempotency key** (D31) — a retry that hashes the same succeeds with 200 + the
original envelope; processing remains at-least-once by cursors (§8 item 4).

**Idempotent emission (D4, D11, D12, D31):** `client_msg_id` is optional but, when
present, unique per `(room, from.seat, client_msg_id)` (unique index). The server
stores the canonical hash (JCS, D31). On a key match: identical hash → 200 with the
original envelope; different hash → 409, nothing stored. A retried POST never
duplicates an envelope; a reused key with new content never silently swallows it —
and under JCS, a legitimately re-serialized retry (different client bytes, same
semantics) hashes the same and succeeds (C14).

**`meta` discipline (normative, D39):** `meta` is optional; when present it carries
exactly one `kind` from the **closed v1 set** — `status`, `handover`, `response`,
`admin-op` — else 422. The server **rejects client-supplied `meta.kind="admin-op"`
from every seat** (Fix A extended, D39); `admin-op` exists only on system envelopes
from `hak` (D6). `meta` is additional data — never conversation content. Recognized kinds:

| kind | Carried by | Fields |
|---|---|---|
| `status` | `type=status` | `state` ∈ {working_on, waiting_on, blocked, done}, `ref`, `note`, optional `eta` |
| `handover` | `type=artifact_ref` | optional `for_seat` (directed handover); makes "open handovers for me" a single filtered pull |
| `response` | `type=task_result`, `type=review_verdict` | marker only — **mandatory at emission** (D13: POST without it → 422); clients MUST NOT auto-respond (§8.2) |
| `admin-op` | system envelopes (`from.seat="hak"`) only | `op` ∈ {member_approve, member_revoke, token_issue, token_revoke, token_revoke_all, token_bootstrap, room_create, charter_update, attachment_delete}, `target` |

**System envelopes (D6, D40):** every admin-privileged operation appends an envelope
with `from.seat="hak"`, human-readable `body`, and `meta.kind="admin-op"` — and the
**mutation and the envelope append run in one transaction (`BEGIN IMMEDIATE`, D40)**:
a partial failure can never leave state changed without audit, or audit without state
change. The room audit trail is therefore replayable like everything else — no side
channel. The `hak` actor holds no token and cannot authenticate; it exists only as
the `from.seat` of these envelopes (D24). Audit scope (D43): the trail records
**successful privileged operations**; failed admin authorization (401/403) is not an
audit event.

## 6. Type vocabulary (v1, closed set)

| type | meaning |
|---|---|
| `chat` | ordinary conversation |
| `status` | heartbeat/status; structured fields in `meta.kind="status"` |
| `task_request` | request for work or status from another seat (expects `task_result`) |
| `task_result` | answer to a `task_request` (threaded via reply_to; `meta.kind="response"` mandatory, D13) |
| `artifact_ref` | pointer to a commit/report/file (+ sha256); `meta.kind="handover"` + optional `meta.for_seat` marks a handover |
| `review_verdict` | structured review outcome (pass/fail + findings pointer; `meta.kind="response"` mandatory, D13) |
| `retraction` | corrects/retracts a prior message (reply_to mandatory; own messages only, admin any, one effective retraction per target, cannot target a retraction — D37) |

The set stays deliberately small. Everything structured-but-unlisted goes through `chat`
plus plain text until the design phase promotes it (fat-event rule: new capability =
new metadata, never a new type — and in v1 the kind set is closed too, D39; room-defined
kinds are a v2 candidate with a charter schema field + validation). Scope events are
**not** envelope types — they live in the scope log (D14).

## 7. Endpoints (v1)

All require `Authorization: Bearer <token>` (except `GET /v1/health`, which is
authenticated too and returns `{"status":"ok","service":"hak","version":"v1"}` —
nothing beyond liveness+identity, D43). JSON in/out.
**Error envelope (D26, normative):** every 4xx/5xx response body is
`{error: {code, message, detail}}` — machine `code`, human `message`, typed `detail`.

**Status-code table (D43, normative):** 200 OK (read, idempotent hit, self-reclaim
refresh, idempotent re-join) · 201 Created (new envelope, new claim, new room, new
upload) · 204 No Content (release) · 400 malformed input · 401 invalid/revoked token
· 403 valid token, no right (pending seat, non-member, wrong seat) · 404 unknown
id/expired claim at transaction start · 409 conflict (scope, idempotency mismatch,
duplicate retraction) · 413 payload too large (body > 64 KB, file > charter cap) ·
422 schema-invalid (client-supplied server fields, unmarked response types,
cross-room file refs, bad kind) · 429 rate-limited (optional limiter, off by default,
D42) · 500 internal.

### Rooms & membership

```
GET  /v1/health                      # authenticated; liveness+identity only (D43)
GET  /v1/rooms    # rooms the token can see
POST /v1/rooms    # admin: {name, charter} — charter validated against §17; operator
                  # MUST be inserted into admins (D32); normalized object stored
GET  /v1/rooms/{room}    # charter (§17), members, admin
POST /v1/rooms/{room}/join    # → pending (member re-join idempotent 200, D36)
POST /v1/rooms/{room}/members/{seat}/approve     # admin
POST /v1/rooms/{room}/members/{seat}/revoke      # admin (kills ALL the seat's tokens, D19)
GET  /v1/rooms/{room}/members    # incl. last_poll (soft presence), last_read_seq
```

**Presence (D27/D43):** any authenticated request from the seat refreshes its
`last_poll` on the room — **activity semantics**, not just message polling; stated
explicitly.

### Messages — push & pull

```
POST /v1/rooms/{room}/messages   # envelope minus seq/id/ts/from/room (D10)
                                 # client_msg_id honored for dedupe (D11/D12/D31):
                                 #   new key + JCS-identical  → 201 with the stored envelope
                                 #   key match, hash same    → 200 with the original envelope
                                 #   key match, hash differ  → 409, nothing stored
                                 #   task_result/review_verdict without meta.kind="response" → 422 (D13)
                                 #   meta.kind="admin-op" client-supplied → 422 (D39)
                                 #   cross-room file reference → 422 (D29)
                                 #   retraction of another seat's message / of a retraction /
                                 #     second retraction of the same target → 409/422 (D37)
                                 #   body > 64 KB → 413 (Q8/D42)
GET  /v1/rooms/{room}/messages   # THE workhorse (pull):
     ?since=<seq> &until=<seq> &from=<seat> &to=<seat|null>
     &type=<t> &thread=<msg_id> &meta_kind=<kind> &for_seat=<seat|me>
     &limit=100 (max 500) &order=asc|desc
GET  /v1/rooms/{room}/messages/{id}
POST /v1/rooms/{room}/read    # {"seq": 4711} → set member's last_read_seq
```

**Pagination (D33, canonical rule):** `since` is exclusive (`seq > since`), `until`
is inclusive (`seq <= until`); bounds are applied **before** ordering and limiting;
`order=asc|desc` affects presentation only; no opaque cursor in v1 because `seq` is
immutable. Filters apply before pagination. New messages arriving between page
requests never affect deterministic traversal (appends only, `seq` immutable).

Pull semantics: `since` returns messages with `seq > since` in ascending order — a
cursor that survives server restarts, client restarts, and gaps. An agent that polls
at every seam never misses anything and never double-processes (idempotent by seq).
A `since` at or above the current max seq returns an **empty 200** — EOF is empty,
never an error (D25). Filters: `meta_kind` and `for_seat` (reserved value `me`
resolves server-side to the token's seat — the token is the only identity carrier
(D10), so `me` cannot be spoofed, D25) make "open handovers for me" one query. The
`thread` filter returns **direct replies only** in v1; full-subtree reconstruction
is a client-side loop over thread pages (D25).

### Scope claims (D2, D14, D15, D16, D22, D34)

```
POST   /v1/rooms/{room}/scopes            # {resource_uri, kind, units?, note?, ttl_min?}
                                          #   new claim           → 201 {scope_id, scope_seq, expires_at}
                                          #   same seat, same resource → 200, refreshes the claim (D16)
                                          #   conflict → 409 {conflicting: {holder, kind, expires_at}}
                                          #   — never silently queued
                                          # ttl_min (D28 Fix B): shorter than the charter value honored;
                                          #   longer clamps to it (response returns actual expires_at);
                                          #   above the hard schema max 1440 → 422
POST   /v1/rooms/{room}/scopes/{id}/renew # extends TTL → 200 {expires_at}
                                          #   only if the claim is live at transaction start (D34);
                                          #   expired/released → 404, no event appended; wrong seat → 403
DELETE /v1/rooms/{room}/scopes/{id}       # release (own claim or admin) → 204
GET    /v1/rooms/{room}/scopes?active=1   # live claims (projector view; presence strip reads this)
GET    /v1/rooms/{room}/scopes?history=1&since=<scope_seq>  # past claims — the provenance
                                          # window (D14), cursor-pullable like messages (D35)
```

- `kind`: `write` | `read-exclusive` | `exclusive` | `share` (D20: `reserve` dropped;
  D34: `share` carries an integer `units` field, default 1 — the `share[n]` enum
  notation is superseded).
- **Atomicity (D15, normative):** the conflict check against live-claim state and the
  claim-event insert run in **one transaction (`BEGIN IMMEDIATE`)**. Liveness is
  derived from events — claim + TTL vs. now — and never waits for stored `lapse`
  markers (lapse is a compaction-time replay-clarity marker, not the expiry
  mechanism). A claim expired by TTL but not yet lapsed is immediately reclaimable.
  Two racing claims yield exactly one 201 and one 409 (C1). Renew is bound by the
  same transactional liveness rule (D34).
- **Conflict matrix (D22, normative, symmetric — D34):** conflict is a symmetric
  relation; the matrix applies direction-independently (the previously unset pairs —
  share vs. write, read-exclusive vs. share — are 409, per the matrix's rows).
  exclusive vs. anything → 409 · write vs. write → 409 · write vs. read-exclusive →
  409 · read-exclusive vs. read-exclusive → 409 (anything less and read-exclusive is
  meaningless) · write vs. share → 409 · share vs. share → allowed while the count
  of concurrent share units on the exact resource stays within the scheme's charter
  capacity (D34); exhausted capacity → 409 carrying the current count in `detail`
  (D26). Same-seat re-claim of the same resource is the one exemption: 200 +
  refresh (D16) — the crash-restart-before-TTL case, safe because only the token
  holder can do it.
- **Resource normalization (D34):** the resource URI must parse; scheme lowercased;
  conflict identity = exact normalized URI; capacity class = scheme (file, gpu,
  host, model); share counting per `(room, resource)`. `gpu://foo` ≠ `gpu://foobar`.
- Claim, renew, release are **events** in the scope log; `expires_at` is derived from
  the last event + TTL. A crashed seat cannot deadlock a resource: the projector
  stops presenting the claim after TTL without any write.
- Convention (charter rule, one line): **write claims are mandatory for repo/tree
  paths**; read seats never claim and are unlimited.

### Files (D29, D30 — room-scoped, grace-protected)

```
POST /v1/files        # multipart upload for a specific room (room in form data);
                      # member status required (D36); size-capped at the charter value → 413
                      #   → {file_id, sha256, size, name, content_type, room}
GET  /v1/files/{id}   # download (content-type preserved); members of the file's room
                      # or admins only — cross-room downloads 403 (D29)
```

**Room-scoped files (D29):** every upload is created for a specific room and can be
referenced only from that room; cross-room references are rejected 422 at envelope
POST. A file is owned by the uploading seat until referenced, then by the room.
"Unreferenced" is defined per-room (no envelope in that room's history carries the
file_id in `attachments` or `refs`; a retracted envelope still counts as a reference,
D23/D17).

**Upload→reference→GC race (D30):** upload and message POST are separate operations,
so an orphan window exists (upload succeeds, POST fails) — expected, bounded by
grace + GC. **Files younger than 24 hours are never GC'd regardless of reference
status** — this closes the race where a sweep deletes a file a concurrent POST is
about to reference. In-flight download serve-through kept (D23).

Large artifacts never go through here: use `refs` with URI + sha256 and keep the
payload in Git / /srv/coding. Uploads are for the screenshot-class of things the
human had to relay by hand. **Retention (D18/Q18, D23, D30):** the **automatic
sweep** (default daily) is the only deleter — attachments unreferenced for 30 days
are removed and each removal is logged as an `attachment_delete` system envelope;
message history stays unlimited regardless. **Quota (D29):** charter
`attachment_policy.max_unreferenced_bytes` (optional, default null) bounds fresh-upload
disk fill per room — D18's age-GC bounds old files, not floods.

### Admin/ops

```
POST /v1/tokens               # admin: issue token for a seat (N per seat allowed, D19);
                              # seat must exist in the host-local seat registry (D43)
POST /v1/tokens/{token_id}/revoke   # kills exactly one token (D19)
hak --bootstrap --seat operator     # host-local CLI (D24): regenerate the operator admin
                                     # token when all admin tokens are lost; appends
                                     # admin-op: token_bootstrap; requires shell access
```

Every admin/ops call appends its system envelope (D6) **in the same transaction as
the mutation** (D40) before returning.

## 8. Delivery semantics

1. **Total order** per room (seq, gapless, single writer). Timestamps are informational;
   `seq` is the order of record (D10, D21).
2. **Broadcast** = visible to all room members (membership-based, not presence-based).
   Presence (last_poll) is cosmetic in v1.
3. **Direct messages** are recorded in the same room history with a `to` field and are
   **readable by all members** — transparent bus, no hidden channels (Q2 proposal).
   If a truly private channel is ever needed, spin up a separate room.
4. **At-least-once processing is the client's job via cursors**; emission is
   **exactly-once logical persistence per idempotency key** (D31) via `client_msg_id` +
   canonical hash (D11/D12). Store your last processed seq, poll `since`, process,
   advance. Server-side `last_read_seq` is for unread/seen UX only (Q6 split).
5. **Immutability:** no edits, no deletes. Corrections are `retraction` messages
   (own messages only, admin any — D37); rendering is visible-but-marked (D17).
6. **No mid-turn push in v1.** Agents poll at seams (turn start/end, tool-call
   boundaries). SSE/long-poll is v2 and only ever an optimization of the same cursor
   semantics.

### 8.1 Cursor discipline (normative — D5)

- **Record your cursor *before* issuing a `task_request`** (subscribe-before-trigger,
  Danwa 2.1): closes the gap between "request sent" and "next poll".
- **Process the batch fully, then persist the cursor.** A crash mid-batch replays from
  the last processed seq (write-ahead discipline; at-least-once processing with
  idempotent handling by seq).

### 8.2 Loop guard (normative — D5, D13, Danwa 2.2)

Messages carrying `meta.kind="response"` (`task_result`, `review_verdict`) MUST NOT
auto-trigger a further response. The marker is **mandatory at emission** (server
rejects unmarked response types with 422, D13) — the guard is exactly as strong as
the marker is reliable. A client may surface response-class messages and act on them
when its user/operator asks; reflex-like polling logic must skip them.

### 8.3 Dispatch table (charter field — Danwa 2.4)

Each room charter records who consumes what. v1 is deliberately trivial:

| seat class | consumes | emits |
|---|---|---|
| human (`operator`) | reads all | `chat` (admin ops are triggered via endpoints; the bus emits their system envelopes — Fix A, D28) |
| agent seats | pull all types | `chat`, `status`, `task_request`, `task_result`, `artifact_ref`, `review_verdict`, `retraction` |

Per-seat `subscriptions` is a v2 candidate. Writing the trivial table down now
prevents implicit conventions later.

## 9. Human Web UI (requirements, not implementation)

- Chat-like view: room list with unread badges, message stream, thread view (reply_to),
- Composer: text, type selector, attach small file, reply/broadcast toggle.
- Admin panel: pending join requests → approve/revoke, token issue/revoke (per-token
  and per-seat), charter display.
- Filters: by seat, type, thread, `meta.kind`. Attachment previews for images (the screenshot case).
- Read state: marks last_read automatically; shows per-member last_poll and last_read.
- **Retraction rendering (D17):** a retracted message stays visible, struck through,
  with an inline link to its retraction envelope; the retraction envelope itself
  always renders. Never hidden — hiding would contradict the transparent-history axiom.
- **Presence strip (memento §4.2):** one line per seat from the latest
  `meta.kind="status"` envelope — current state + ref — beside the live scope claims
  (`GET /scopes?active=1`). **Staleness (D27):** a seat renders gray when its
  `last_poll` is older than 15 minutes (recorded default, cosmetic only). **`done`
  clears the line — a UI projection rule (D43):** the status is still recorded in
  history; the strip chooses not to display it.
- **`blocked` status (Q16, go-gate):** notify vs. badge is an operator preference —
  the go message decides (M2); both render in the presence strip regardless.
- **Rendered-link scheme allowlist (D43):** `refs`/`uri` fields render as links only
  for allowed schemes (http/https/git/ssh/file); all other schemes render as plain
  text — the `javascript:` catch is real for a web UI.
- **Attachment names are display-only (D43):** never a filesystem path.

## 10. Agent client guidance

- Token in env var (`HAK_TOKEN`), base URL in (`HAK_URL`, e.g. `http://gx10:8890`).
- Poll at **seams**: turn start (catch up: `GET messages?since=<cursor>`), after finishing
  a work item (`status` or `task_result`), before ending the turn.
- Prefer filtered pulls (`type=status`, `meta_kind=handover&for_seat=me`) over full-history reads.
- Record `backend` in every message (convention from IDENTITIES.md — same as commit trailers).
- Honor §8.1/§8.2 cursor discipline and loop guard; send `meta.kind="response"` on
  every `task_result`/`review_verdict` or the server rejects the POST.
- Never send `from`, `room`, `seq`, `id`, `ts` — the server owns all five (D10).
- Uploads are room-scoped: upload with the target room in the form data, then
  reference the returned file_id from that room only (D29).
- **Claim before you write** (charter rule): `POST /scopes` with `resource_uri=file://...`
  before touching a repo/tree; renew as part of the working loop; release when done.
- Minimal client is five calls (memento §5): `claim(resource)`, `renew()`, `release()`,
  `status(state, ref)`, `pull(since)` — invoked at seams.

```bash
curl -s "$HAK_URL/v1/rooms/bdh-cl-development/messages?since=$CURSOR&limit=200" \
```

## 14. Security notes

- **Provenance is server-owned (D10):** `from` derives from the token, `room` from the
  path, and `seq/id/ts` are server-assigned; client-supplied values for these five
  fields are rejected 422. No seat can speak as another seat; mixed-seat clock skew
  cannot bend the audit trail (D21).
- Tokens: 32+ random bytes, shown once, stored hashed **SHA-256, unsalted** (D43) —
  256+ bits of entropy; no realistic preimage/rainbow exposure; password-KDFs are
  overkill; revisit only if tokens become human-memorable. Revocation is immediate
  (per-token or per-seat, D19) — a revoked token gets 401 on its next request (D24).
  Issuance is bound to the host-local seat registry (D43).
- LAN-only bind; optional TLS via reverse proxy (v2); no public exposure, ever.
- **Files are room-scoped (D29):** uploads require member status; downloads require
  membership in the file's room or admin; cross-room references rejected at envelope
  POST; 24-hour upload grace bounds the reference/GC race (D30). Served only from
  the uploads dir with generated names; no path traversal; size cap enforced before
  accept → 413; MIME not trusted for execution; `content_type` is descriptive (D7),
  never an execution hint; attachment `name` is display-only, never a filesystem
  path (D43). Age-GC deletion runs as the automatic sweep — the only deleter — and is
  logged as a system envelope per file, transactionally bound (D18/D23/D40).
- The message history is the audit trail — append-only by design; admin-privileged
  operations are system envelopes in the room they affect (D6), bound to their
  mutations in one transaction (D40), not log lines elsewhere. Audit scope (D43):
  the trail records successful privileged operations; failed admin authorization
  (401/403) is not an audit event.
- **Recovery (D24):** if all admin tokens are lost, the host-local CLI
  `hak --bootstrap --seat operator` regenerates the operator admin token and appends
  `admin-op: token_bootstrap`. It requires shell access to the host — deliberate: on
  a LAN-only single-process service, the host shell *is* the trust root. No new
  endpoint, no remote recovery path.
- **Error envelope (D26):** every 4xx/5xx response body is `{error: {code, message,
  detail}}` — uniform shape for clients, typed detail for diagnosis. Status-code
  semantics are tabulated in §7 (D43).
- Scope claims carry no authority: they are coordination signals, not locks. A claim
  does not (and cannot) enforce anything at the filesystem level; enforcement remains
  seat discipline + review, exactly as today — the claim makes the discipline *visible*.

## 15. Acceptance criteria (normative — gate v1; the conformance script ships with the implementation and must pass C1–C18, D41)

- **C1 Scope conflict (racing):** two concurrent exclusive claims on one resource →
  exactly one 201 and one 409 (single-transaction check+insert, `BEGIN IMMEDIATE`);
  the 409 carries holder + expiry; both events visible in the scope log. A claim
  expired by TTL but not yet lapsed is immediately reclaimable (liveness derives
  from events + TTL, never from lapse markers). The conflict matrix (D22) is
  exercised across all its rows in the conformance script (each 409 row + the
  share-capacity row with its count-carrying 409).
- **C2 Crash safety + self-reclaim:** a claim without renewal expires via the
  projector ≤ TTL after process death; the resource is reclaimable without admin
  action. A same-seat re-claim of its own live claim returns 200 and refreshes the TTL.
- **C3 Handover determinism:** after an `artifact_ref` with `meta.kind="handover"`
  lands, the named seat's next seam-pull returns it (send, pull with fresh cursor,
  assert presence and order).
- **C4 Presence strip:** live states for ≥ 2 concurrent seats; a `done` status clears the line.
- **C5a Replay determinism (envelopes, D31 reworded):** **canonical-JSON**
  re-serialization of every envelope — using the **same canonicalization rule as the
  idempotency hash (RFC 8785 JCS)** — is byte-identical on rebuild from seq 0.
- **C5b Replay determinism (state):** projector state hash equal before and after
  rebuild from the logs alone (messages + scope events) — the derived view, not the
  log bytes, is what must reconstruct.
- **C6 Idempotent emission:** the same `client_msg_id` POSTed twice with identical
  body → one envelope, two 2xx responses naming the same `id` (uniqueness key: room,
  seat, client_msg_id). The same key with a different body → 409, nothing stored.
- **C7 Cursor discipline:** a client crash mid-batch replays the full batch from the
  last persisted cursor; nothing between cursors is lost (replay over a kill -9 of the
  reference client).
- **C8 Loop guard, both halves:** (a) a `task_result` addressed to a reflex-polling
  reference client never produces a second automated response; (b) an unmarked
  `task_result`/`review_verdict` (no `meta.kind="response"`) is rejected 422 at POST.
- **C9 Retraction rendering:** a retracted message remains rendered with visible
  retraction marking and a link; the retraction envelope itself always renders.
- **C10 Server-owned provenance:** a POST carrying client-supplied
  `from`/`room`/`seq`/`id`/`ts` is rejected 422 and nothing is stored; a forged
  `from.seat` never reaches the log; the stored envelope shows the server-derived
  values.
- **C11 Membership state machine (D36):** pending/valid → 403 off-join; member/valid
  → normal; revoked/valid → 403; any/revoked-token → 401; revoked-seat rejoin → new
  pending row; member re-join idempotent.
- **C12 File authorization (D29):** room members download; cross-room download 403;
  cross-room reference at POST 422; pending-seat upload 403.
- **C13 Upload→reference→GC race (D30):** upload, then concurrent reference + sweep —
  a file younger than 24h survives the sweep; an unreferenced file past 30 days is
  gone and its `attachment_delete` envelope exists; an in-flight download serves through.
- **C14 Canonical-JSON idempotency equivalence (D31):** a retry with semantically
  identical but differently-serialized body (re-ordered keys, omitted-vs-null optional
  fields) hashes the same under JCS → 200 with the original envelope; a semantic
  change → 409.
- **C15 Pagination semantics (D33/D35):** `since` exclusive, `until` inclusive;
  bounds before order/limit; `order=desc` preserves bounds; empty 200 at/above max
  seq; scope history `since` mirrors messages.
- **C16 Renew liveness (D34):** renew after expiry → 404 + no event; renew vs.
  concurrent reclaim race → exactly one winner under `BEGIN IMMEDIATE`; wrong-seat
  renew → 403.
- **C17 Retraction authorization (D37):** own-message retraction 201; other-seat
  message retraction 403 (admin any); retraction-of-retraction 422; second retraction
  of the same target 409 with pointer to the effective one.
- **C18 Admin invariants + admin-op atomicity (D32/D40):** every room has `operator`
  in `admins` after creation; `admins` is the sole authority source (implicit grant
  removed); a mutation without its envelope (induced partial failure) never commits;
  sweep deletion + envelope atomic.

## 17. Charter schema (normative — adopted v0.4, amended v0.5)

### Normative description

The **charter** is the single authoritative document for a room. It is created with
the room (`POST /v1/rooms`) and returned by `GET /v1/rooms/{room}`. **In v1 the
charter is immutable after creation** (D32); a future mutation endpoint MUST go
through the service and emit a system envelope with `meta.kind="admin-op"` and
`op="charter_update"` (D28 boundary note stands: never direct SQLite writes).

**Admins (D32):** room creation MUST insert `operator` into `admins`; `admins` is
the sole authoritative admin set. Bootstrap invariant: every room always has
`operator` in `admins`.

Charter fields control: identity and purpose of the room; the admin list; the trivial
dispatch table (§8.3); optional linkage to a Git repo / project; claim policy
(default TTL + share capacities); attachment policy (size cap + optional
unreferenced-bytes quota); the standing charter rule that **write claims are
mandatory for any `file://` path under a repo/tree**.

Membership is *not* stored inside the charter; it is derived from the membership
table (join → pending → approved, D36). The charter records the initial admin list
and the dispatch rules.

### Implementation notes

- On `POST /v1/rooms` the server validates the charter against this schema, inserts
  `operator` into `admins` if missing (D32; the creating admin is also injected), and
  stores the whole object (or a normalized version) in the rooms table.
- `GET /v1/rooms/{room}` returns the charter plus the derived membership list and
  live projector data (last_read, last_poll, active scopes count, etc.).
- The charter is **immutable after creation in v1** (D32). Any later mutation (v2+)
  must go **through the service** and emit an `admin-op: charter_update` system
  envelope so the change is part of the auditable history (D6/D28/D40). Direct
  SQLite writes are a rejected charter-update path (boundary note).
- The `dispatch` table is deliberately trivial and constant for v1; the schema still
  records it so future per-seat subscriptions have a clear extension point.
- Room-scoped files (D29): uploads carry the room in form data; the charter's
  attachment policy bounds them; the 24h grace (D30) protects the reference window.
